# 底盘交互控制改造计划

## 目标

在 Ubuntu 22.04 / ROS Humble 与 Ubuntu 24.04 / ROS Jazzy 上，启动上位机与下位机 USB 通信后保持待命。操作员通过 CLI 或 Web GUI 输入 `vx vy wz amax jerkmax`，上位机生成加速度与 jerk 受限的速度序列，经现有 ARES USB 协议发送给底盘。不依赖定位或仿真。

单位：`vx`、`vy` 为 m/s；`wz` 为 rad/s；`amax` 为 m/s²；`jerkmax` 为 m/s³。`amax`、`jerkmax` 约束平面速度向量。角加速度和角 jerk 使用独立配置值。五个输入是上位机目标，不改变固件当前的三或四 float 速度帧格式。

## 架构

- **控制核心**：唯一的速度帧生产者。持有当前指令、目标、加速度状态、控制权和链路状态；固定周期生成速度。CLI 和 Web GUI 都调用它的控制接口。
- **USB 桥**：负责 `1209:0001`、DataID、三/四 float 格式和 USB 反馈。不生成目标，也不在超时或析构时补发零帧。
- **CLI**：交互输入五个参数；提供 `status`、`stop`、`halt`、`quit`。`stop` 是明确请求受限减速到零，`halt` 是明确请求立即发送零目标。
- **Web GUI**：与 CLI 使用同一接口。显示控制权、USB 链路、目标速度、实际下发速度和事件。参考本机 `SF-Gallery` 的字体层级、语义色、间距和组件行为；不把下发速度标成实测车速。

## 控制权与断联

同一时间只有一个操作端持有控制权。控制权由显式取得和释放管理；失去操作端连接后停止生成与发送速度帧。恢复连接需要重新取得控制权并发送新目标，不重放旧目标。

启动待命、操作端断联、指令源失活、USB 发送失败和进程退出都不自动发送零速度帧。只有显式 `stop`、`halt` 或操作员输入零目标会产生零速度帧。桥接现有的“50 ms 后发零”和析构发零逻辑需要移除。断联后应停止相关 TX；是否需要停止协议心跳，取决于下位机实际超时机制。

必须核对并记录下位机对“速度帧超时”和“心跳超时”的行为。当前仓库不含完整固件源码，因此在该机制被证实前，不把停止发送解释为底盘已停车，也不进行无保护的实车断联试验。

## 实施顺序

1. 精简现有实验与分析入口，保留可复用的 USB 协议和构建支持。
2. 实现共享控制核心：目标更新、平面加速度与 jerk 限幅、角速度独立限幅、显式停车、控制权状态。
3. 修改 USB 桥的待命、断联及退出行为，确保不自动发零、不重放旧帧。
4. 实现 CLI 和 Web GUI，共用同一控制接口；Web 页面采用本地 `SF-Gallery` 的视觉语言。
5. 更新 launch、参数文件、README 和验证脚本。
6. 验证限幅曲线、双端控制权、USB 帧格式、启动待命、断联无自动零帧及重连不重放。确认下位机超时机制后再做低速实车验证。

## 验收

- 不启动定位、IMU 或模拟组件即可运行控制服务。
- CLI 与 Web GUI 的同一指令产生相同的速度序列，且不会同时控制。
- `amax`、`jerkmax` 限制的是上位机下发曲线；`wz` 使用独立角限值。
- 启动和断联不产生自动零帧；显式停车按命令执行。
- USB 发送失败后旧命令不会在重连后重放。
- Ubuntu 22.04 / Humble 构建与自动测试通过；Ubuntu 24.04 / Jazzy 在可用环境中验证。
